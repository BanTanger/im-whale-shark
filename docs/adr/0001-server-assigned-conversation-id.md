# 单聊会话 ID 由服务端分配，不由双方 uid 推导

单聊的 `convId` 由服务端在首次发起会话时分配并落库（`conversation` 表 + `uk_single(app_id, uid_a, uid_b)` 唯一约束），不使用 `hash(min(uidA,uidB), max(uidA,uidB))` 这类可从双方 id 推导的方案。

## Considered Options

**推导哈希**：双方各自算出同一个 `convId`，省掉会话表与一次写。
否决原因：它把「删好友后重新加，聊天记录是否延续」这个产品问题**永久锁死**成一个技术事实——哈希不变，历史必然延续；哪天想「重新开始」就无解。而会话表只多一次 insert + 一个唯一约束。

**独立会话表**：`convId` 是服务端分配的独立标识（雪花或自增），`(app_id, uid_a, uid_b)` 唯一约束保证同一对用户不会重复建会话。
采纳原因：会话的生命周期可以独立于用户关系；`convId` 从"用户关系的函数"变成"一个实体"，后续加"免打扰会话""归档会话""按会话付费"都不用动 id 生成规则。

## Consequences

- 建会话需要一次写与一次唯一冲突处理：并发首次发消息时用 `INSERT ... ON DUPLICATE KEY` 或捕获唯一冲突后回查。
- 客户端不能自己算会话 id，必须由服务端返回；SDK 的 `sendMessage(toUid)` 需要内部完成"解析或创建会话"这一步。
- `convId` 同时是消息表的分区键，一旦分配就不再变——这也意味着会话不能迁移到别的分区，验证了"会话不重建"的取舍。
