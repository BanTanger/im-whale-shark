# 网关用 JWT 验签鉴权，不查 Redis session

登录成功后服务端签发 JWT（有效期 15 分钟，`jti` 唯一），网关本地验签即可放行；刷新 token 换新 JWT；踢人靠一份**只记录被踢 `jti` 的小黑名单**（Redis + 本地负缓存），而不是把整张 session 表搬到 Redis。

## Context

网关的热路径预算是**每条消息 10 µs**（§9），任何一次 Redis 往返（约 100 µs）都会让吞吐掉一个数量级。但「踢下线」和「强制登出」又必须能立刻生效。

## Considered Options

- **Redis session token，每条消息查一次**：能即时吊销，但每条消息一次 Redis 往返，直接违反热路径约束。否决。
- **纯 JWT，无吊销**：零查库，但踢人要等 token 自然过期（最长 15 分钟），安全事件下不可接受。否决。
- **JWT + 短有效期 + 刷新 + 踢人黑名单**（采纳）：验签是纯 CPU 操作；黑名单只包含"被主动踢掉的 jti"，数量极小，可以整体缓存在网关本地，按 1 秒同步一次。

## Consequences

- **token 有效期决定了踢人的最坏延迟**：15 分钟。需要更强保证时缩小有效期，代价是刷新更频繁。
- 刷新 token 的存储仍是 Redis（低频操作，不在热路径），`jti` 与设备绑定，便于多端管理和单点登出。
- 网关必须实现"黑名单本地缓存 + 增量同步"，这是新增的一段状态；它按秒级最终一致，接受"踢人后 1 秒内仍可能收到消息"。
- 密钥轮换需要支持多公钥并存（`kid` 头），否则轮换期间全部断连。
